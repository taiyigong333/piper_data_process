# 项目交接

## 目标

将 `/home/ubuntu/gcj/projects/data_collect/data/corm_in_plate` 下由 Piper 采集的 HDF5 轨迹，转换为本地 LeRobot v2.1 数据集，以便 OpenPI 微调读取。

## 关键契约

1. 依赖版本：`pyproject.toml` 固定 LeRobot Git 提交 `0cf864870cf29f4738d3ade893e6fd13fbd7cdb5`，并固定 `datasets==3.6.0`；两者都与 `openpi/uv.lock` 一致，避免 LeRobot 数据加载 API 漂移。`imageio-ffmpeg==0.6.0` 提供项目内的静态 FFmpeg。
2. 原始数据：相机约 30 Hz，机器人约 60 Hz。转换不使用采集端已写入的 `*_align` 序列，而是使用 `*_raw` 与 `camera_observations/timestamp` 重新执行因果对齐。
3. 对齐策略：默认 `previous`，即 `state_timestamp <= image_timestamp` 的最后一条状态；状态年龄超过采集 YAML 的阈值时失败，防止质量问题被隐藏。
4. 行为监督：采集数据存储的是物理反馈而非下发控制目标，因此动作定义为下一图像时刻的反馈状态。默认数据集保存绝对关节目标与绝对夹爪开度；OpenPI 训练端可对前六维关节做相对动作变换。
5. 训练字段：LeRobot 原始相机字段为 `image` 与 `wrist_image`，数值字段为 `state` 与 `actions`。OpenPI 的 `LeRobotLiberoDataConfig` 会将相机字段映射为内部的 `observation/image` 与 `observation/wrist_image`。
6. 写入安全：数据集先写入与目标同级的唯一暂存目录，只有全量轨迹成功才原子替换目标目录；异常时现有完整数据集不会被覆盖。
7. 视频编码：`use_videos: true` 时，转换器替换固定 LeRobot 提交的编码入口，调用 `imageio-ffmpeg` 的静态 FFmpeg 和 `libx264`，不会调用系统 `ffmpeg`。默认图片模式用于当前机器的 OpenPI 训练。

## 操作顺序

1. `uv sync --group dev` 创建 Python 3.11 环境。
2. 用 `--max-episodes 1` 运行转换，检查输出 `meta/info.json`、`conversion_manifest.json` 和抽样图像。
3. 全量运行转换。默认 `overwrite: false`，现有产物会被拒绝覆盖。
4. 在 `openpi` 中让训练配置使用 `repo_id: "taiyigong333/piper_corn_in_plate"`，并设置 `HF_LEROBOT_HOME=/home/ubuntu/gcj/projects/data_collect/data_processed/datasets`。标准 LeRobot 加载器会由该目录自动解析到 `datasets/taiyigong333/piper_corn_in_plate`；可执行的 π₀-FAST 与 π₀.₅ 配置和训练命令见 [OpenPI训练说明.md](OpenPI训练说明.md)。

## 风险与待确认

- 系统 `ffmpeg` 因动态库冲突无法使用；转换器不依赖它。项目内静态 FFmpeg 的版本与路径可通过 `uv run piper-project-ffmpeg --check` 验证。
- 当前 LeRobot 默认 `torchcodec` 视频解码仍会链接系统动态 FFmpeg，无法读取 MP4；因此在该机器进行 OpenPI 训练时保持 `use_videos: false`。MP4 转换已验证可用，适用于导出和归档。
- 默认文件保存绝对关节动作。若改用 TCP 相对动作，只有 `xyz_rxryrz` 可在转换器中做欧拉角回绕；四元数 TCP 需要专门的 SE(3) 相对变换。OpenPI 现有 `extra_delta_transform` 仅适用于默认的六维关节空间。
- 采集配置记录的相机色彩字段未参与解码：HDF5 内已是 JPEG，比特流由 Pillow 直接解码为 RGB，避免二次通道交换。
